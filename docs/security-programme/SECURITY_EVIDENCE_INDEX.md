## 2. Resolution of Inter-Report Conflicts

1. **Conflict 1 — Direct Exploitability of `POST /api/v1/billing/payments/verify` with Paystack (`EV-05 CRITICAL-02` vs `EV-06 CF-01` & `NEW-01`)**:
   - *Conflict*: `EV-05` claimed a Paystack reference could be replayed infinitely on `/api/v1/billing/payments/verify`. `EV-06` proved that [`billing.mjs:121`](file:///c:/Users/John/Documents/CODE/back/bettingAutomationBackend/src/api/routes/billing.mjs#L121) checks `tx.data?.status === 'successful'` (Flutterwave's status string), whereas Paystack returns `'success'`, breaking legitimate Paystack verification on `/verify` while leaving Flutterwave (`tx_ref` vs numerical `id`) and cross-path (webhook `inv-${reference}` vs verify `inv-${id}`) replayable.
   - *Resolution*: **Both the functional bug and the security vulnerability are real.** We fix Paystack status/minor-unit normalization in `billing.mjs` AND enforce canonical multi-alias payment reference locking (`reference`, `inv-${providerRef}`, `inv-${providerTxId}`) inside `applyPaymentSuccess` so no transaction can ever be redeemed twice across any combination of webhook or `/verify` calls.
2. **Conflict 2 — `POST /payments/checkout` Unauthenticated Impact (`EV-05 HIGH-09` vs `EV-06 CF-04`)**:
   - *Conflict*: `EV-05` claimed `/payments/checkout` leaked another user's payment reference in the HTTP response. `EV-06` proved the response only returns `{ checkoutUrl }` ([`payments.mjs:31`](file:///c:/Users/John/Documents/CODE/back/bettingAutomationBackend/src/api/routes/payments.mjs#L31)), though the reference is embedded in the provider redirect URL and unauthenticated checkout creation pollutes `audit_logs`.
   - *Resolution*: Require `operatorAuth` on `POST /payments/checkout` and bind `accountId` strictly to the authenticated principal (`req.accountId`).
3. **Conflict 3 — Support Ticket Read Visibility (`EV-05 HIGH-12` vs `EV-06 CF-05`)**:
   - *Conflict*: `EV-05` claimed `POST /api/v1/support/channels` allowed reading other users' support tickets. `EV-06` proved [`support/service.mjs:10`](file:///c:/Users/John/Documents/CODE/back/bettingAutomationBackend/src/domain/support/service.mjs#L10) filters `support_messages` by `WHERE account_id = $1`, so the impact is global `support_channels` table pollution/injection, not cross-tenant message reading.
   - *Resolution*: Restrict `POST /api/v1/support/channels` to `requireAdmin('SUPER_ADMIN')`.
4. **Conflict 4 — KMS Master Key Fallback (`EV-05 MEDIUM-01` vs `EV-06 CF-07`)**:
   - *Conflict*: `EV-05` cited `src/crypto/kms.mjs:17` as having a deterministic seed fallback. `EV-06` verified `src/crypto/kms.mjs` already throws at startup if `KMS_LOCAL_SECRET` is unset, whereas [`src/domain/betting-accounts/service.mjs:25`](file:///c:/Users/John/Documents/CODE/back/bettingAutomationBackend/src/domain/betting-accounts/service.mjs#L25) still had a hardcoded `'betting_automation_master_vault_key_32'` fallback.
   - *Resolution*: Remove the hardcoded fallback in `betting-accounts/service.mjs:25` so vault encryption fails closed unless `KMS_LOCAL_SECRET` is configured.
